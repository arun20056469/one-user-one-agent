# Known Limitations

Written to be useful in a technical discussion, not to hide anything. Each item
says what is limited, why, and what we would do next.

## 1. The data pack is a faithful **stand-in**, not the official ZIP

The assignment's data-pack ZIP was never made available to us, so the pack in
`data_pack/` is generated by `tools/generate_datapack.py` from one seed. It is
built to match the documented schema and to contain **every** documented trap
and replay surprise:

- duplicate `event_id`s, late events, wrong phone clocks, months of history
- offline-buffered app opens (days old and 5–30 min old)
- a day-stale profile snapshot with duplicate rows and missing rows for new users
- dialect conflicts across app setting / profile / campaign deeplink
- language variants sharing a `content_slug`; availability windows; mid-day
  withdrawals
- prompt-injection text hidden in catalogue descriptions
- an unmeasurable goal and two underspecified goals
- a biased pilot report
- `replay/` triggers, live events, control events and model faults
- the 14-day behaviour simulator (`simulator/simulate_outcomes.py`)

**Consequences.** Every number in `sample_run/` is a property of *this* pack and
the simulator, not of real users. The code is data-driven and reads the pack
format dynamically, so dropping in the real pack should work with little or no
change — but that is an expectation, not a verified fact, and any schema
deviation will need a small loader fix. `Pack.__init__` fails fast with a clear
message if `config/goals.json` is missing.

## 2. The model contributes almost nothing (by design, and honestly)

The default provider is a **mock/replay** provider: it echoes the rule plan with
deterministic noise, and reproduces the injected faults. There is **no real LLM**
in the delivered run, so the measured impact is essentially the *rule planner's*
impact. This is deliberate — it guarantees the run is reproducible with no API
key — but it means the submission does not demonstrate that a language model
improves outcomes. A real provider can be dropped in behind
`ModelProvider.propose()`; everything downstream (verifier, budgets, fallbacks)
is already in place.

## 3. The simulator is provided, deterministic, and not ground truth

`simulate_outcomes.py` is the assignment's stand-in for user behaviour. Uplift
figures are therefore artefacts of that script, and evaluators deliberately
rerun it with a new seed and an unseen replay day. Our judge reads both
simulator outcome events and real pack events inside each goal window, but it
cannot validate the simulator's assumptions.

## 4. The honest result is "no detectable effect yet"

On the delivered run: ITT **−0.38 pp (95% CI [−4.08, +3.32]**, agent 5.15%
n=719 vs holdout 5.52% n=181**)**. The interval crosses zero. With ~900 triggers
on a single replay day this is expected: the study is underpowered. We report
this as **"no detectable effect yet"** rather than dressing it up. The
per-goal cells are even smaller and are reported only to show where a signal
*would* come from; none is individually conclusive.

## 5. One replay day, limited observation

The replay is a single day. Goals have multi-day windows (3–14 days), so even
with the 14-day simulator many windows sit at the edge of the observation
horizon; the judge correctly returns `INCONCLUSIVE` rather than guessing, but
that also limits how many goals can be judged at all. A real evaluation needs
multiple days and far more triggered viewers.

## 6. Rules we implemented, and rules we would need to extend

- **Eligibility** supports the predicates present in `config/goals.json`
  (`min_age_days`, `subscription_in`, `never_completed_any_episode`,
  `has_play_no_complete`, `completed_episode_count_in`,
  `recent_search_no_play_hours`, `dormant_days`, consent flags). An eligibility
  key we do not recognise is currently **ignored** (treated as not restricting),
  which is the safe-in-the-wrong-direction default: a new goal with an unknown
  guard could be judged eligible when it should not be. The verifier re-derives
  eligibility but shares the same predicate set. **Next step:** fail closed on
  unknown eligibility keys.
- **Success rules** support `min_count`, `match` on `props`, `distinct_days`
  and `requires_play_same_day`. Arbitrary nested rules are not handled.
- **Home-page content** is chosen by deterministic rules (unfinished episode →
  same genre → popularity → new releases → genre rows). It is not learned and
  not personalised beyond these rules.

## 7. Messaging and copy are deliberately conservative

- Push copy and WhatsApp variables are assembled only from the catalogue and
  `config/pricing.json`; the only three prices are ₹1/₹149/₹399. We never
  generate free text, which removes the risk of inventing offers or episodes —
  at the cost of less natural copy.
- WhatsApp uses only the three approved templates.
- Delivery is only "confirmed" conceptually by `message_delivered`; the
  simulator's delivery modelling is coarse, and we do not retry undelivered
  messages.

## 8. Latency and scale

- `decided_in_ms` measures **in-process processing time** (`time.perf_counter`),
  not queueing or network time. The datastore-slow window is modelled with an
  artificial sleep, not a real database under load.
- The replay is **single-threaded and ordered** (a faithful replay of one day).
  The design *intends* to scale by partitioning per viewer and skipping optional
  model calls under load, but we have **not** demonstrated 1,000 simultaneous
  opens, let alone 10 million users / 40 dialects. Trading off model quality for
  latency under surge is implemented; horizontal scaling is not.
- Only the six dialects `d1–d6` from the pack config are handled.

## 9. Safety checks are strong but not exhaustive

- The prompt-injection detector is a **pattern list** over catalogue
  descriptions. A novel phrasing could go unflagged — though the system never
  treats any catalogue text as an instruction regardless, so the blast radius is
  small (the flag is for logging/auditing).
- Equal timestamps have no deeper tie-break than insertion order.
- There is no authentication or rate-limiting API layer; the deliverable is the
  CLI and the replay harness, not a served product.

## 10. What we would do with the real pack and more time

1. Drop in the real pack and diff the trap counts; fix any loader assumptions.
2. Add a real model provider behind the existing interface and A/B it against
   the rule path with the verifier unchanged.
3. Fail closed on unknown goal-eligibility keys; add rule-schema validation.
4. Run multiple replay days and pool the ITT estimate to get a usable CI.
5. Add a concurrency/load test (1,000 opens/minute) and a cost budget for model
   calls under surge.
